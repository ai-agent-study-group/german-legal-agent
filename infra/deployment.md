# MVP 배포 검토

상태: **Railway 기준 준비 중**. 공개 범위와 실제 서비스 설정은 미확정이며 배포가 완료되었다는 뜻은 아닙니다.

## 실행 단위

- 현재 웹 데모는 `web/`의 Next.js 앱과 `/api/chat` 데모 API입니다. 별도 FastAPI 백엔드가 존재하지만 이 PR의 웹 컨테이너에는 포함되지 않으며 배포·연동 방식은 미정입니다.
- `web/package-lock.json`을 사용하고 Node.js 20.9 이상에서 `npm ci`, `npm run build`로 빌드합니다. CI는 Node.js 20을 사용합니다.
- 모델은 현재 `AGENT_PROVIDER=demo`만 지원하며 실제 AI 답변이 아닙니다. 실제 제공자와 키는 추후 별도로 결정합니다.
- `docs/`의 GitHub Pages는 서비스 배포와 별개입니다.

## Railway 배포 경로

Railway에서 GitHub 저장소를 연결하고 서비스의 Root Directory를 `web`으로 지정해 `web/Dockerfile`을 빌드합니다. Railway가 주입하는 `PORT`로 서버가 `0.0.0.0`에 수신합니다. 별도 Docker Hub 게시나 Compose는 필요하지 않습니다. 프로젝트·계정 소유자, 예산, 공개 범위, 자동 배포와 PR 미리보기 사용 여부는 팀에서 확정해야 합니다.

로컬에서는 저장소 루트에서 다음과 같이 확인합니다.

```sh
docker build -t german-legal-web:local web
docker run --rm -p 3000:3000 -e PORT=3000 german-legal-web:local
```

이미지는 standalone Next.js 서버와 검토된 데모 자료만 포함하며 non-root 사용자로 실행됩니다. 로컬 `.env`와 검토 대기 자료는 빌드 컨텍스트에서 제외합니다. Railway에서 서비스 생성, 도메인 발급 및 실제 배포는 별도 접근 권한과 공개 범위 확인 후 진행합니다.

이미지가 준비된 뒤 페이지·데모 API를 확인하는 명령과 기대 결과는 [웹 컨테이너 로컬 테스트 가이드](container-smoke-test.md)를 참고합니다.

현재 `/admin`은 숨겨진 링크일 뿐 인증이 없습니다. 공개 범위를 결정할 때 이 경로와 개인정보 처리 기준을 함께 검토해야 합니다. 별도 백엔드의 서비스 경계와 통신·비밀값 설정은 팀에서 결정해야 합니다.

## 배포 후 확인 후보

실제 플랫폼을 정하면 다음 절차를 해당 환경에서 실행하고 결과, 배포 URL, 담당자와 날짜를 기록합니다.

1. 배포된 커밋과 빌드 성공 여부를 확인합니다.
2. `/`, `/housing`, `/visa`가 열리고 정적 자산이 로드되는지 확인합니다.
3. 데모 질문을 보내 `/api/chat`의 정상 응답과 출처 표시를 확인합니다. 민감한 실제 사례는 입력하지 않습니다.
4. 실패한 배포에서 이전 정상 배포를 복원하고 위 확인을 반복합니다. 플랫폼별 복원 절차와 담당자는 선택 후 기록합니다.

전용 health/readiness 엔드포인트의 필요성과 의미는 배포 플랫폼 및 백엔드 구조가 정해진 뒤 결정합니다. 화면 응답만으로 외부 모델이나 데이터 소스의 상태까지 보장하지 않습니다.
