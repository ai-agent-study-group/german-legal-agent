# 백엔드 선택: Python과 Next.js

상태: **비교 자료 · 선택 미정**. 아래 장단점과 의견은 팀 논의를 위한 판단이며 확정 설계가 아닙니다.
정확히는 Python이라는 언어와 Next.js라는 프레임워크의 비교입니다.
여기서는 **Python 별도 서버(예: FastAPI)**와 **Next.js의 TypeScript 서버 기능 유지**를 비교합니다.

## 두 선택지

| 관점 | Python 별도 서버 | Next.js 서버 기능 유지 |
| --- | --- | --- |
| 현재 데모 활용 | TypeScript API·agent의 이식 또는 재작성 필요 | 기존 API·agent 인터페이스를 바로 활용 가능 |
| 자료 수집·AI 작업 | Python 수집 코드와 언어를 맞출 수 있음. 필요한 라이브러리부터 확인 | TypeScript로 모델 호출·도구 실행 가능. Python 수집은 별도 유지 가능 |
| 웹과 연결 | API 요청·응답 계약과 서버 간 연결 필요 | 웹·서버를 한 프로젝트에서 개발하기 쉬움 |
| 협업·학습 | FE·BE·데이터 영역을 명확히 나누는 실습에 유리할 수 있음 | 초기 연결 작업을 줄일 수 있음. 한 프로젝트 안에서도 모듈·담당 분리 가능 |
| 실행·운영 | 웹과 Python 환경, 두 서버의 실행·배포를 관리 | 웹과 API를 함께 운영 가능. 수집 작업의 실행 환경은 별도 고려 |
| 오래 걸리는 작업 | API와 워커를 나눌 수 있으나 Python 선택만으로 해결되지는 않음 | 별도 워커를 둘 수 있음. 호스팅별 요청 시간·파일 저장 제약 확인 필요 |
| 핵심 확인 | 팀의 Python 경험, 별도 API 학습 목표, 추가 운영 부담 | 팀의 TypeScript 경험, 필요한 AI 기능·배포 환경의 지원 여부 |

FastAPI는 Python 타입 선언 기반의 입력 검증과 자동 API 문서 기능을 제공합니다.
Next.js Route Handler도 HTTP API를 만들고 외부 백엔드에 요청을 전달할 수 있습니다.
따라서 “agent이므로 Python 필수”나 “Next.js는 화면만 가능”이라고 정할 필요는 없습니다.

## 이 팀에 대한 잠정 의견

협업으로 역할을 나누고 자료 수집·agent·운영을 경험하는 것이 우선이라면,
**웹은 기존 기반을 활용하고 Python 백엔드를 별도로 두는 안을 먼저 검토할 만합니다.**
이미 Python 수집 예제가 있고 AI·데이터·MLOps에 관심 있는 참여자가 있다는 점을 고려한 의견입니다.
관심 분야만으로 Python 숙련도를 가정하지 않으며, 추가 서버 운영과 기존 agent 이식에 드는 시간도 확인해야 합니다.

빠르게 실제 모델을 연결한 첫 시연이 가장 중요하다면 **기존 Next.js 서버 기능을 유지하는 안**이 초기 작업은 적습니다.
폴더 분리 자체를 위해 서버를 추가할 필요는 없습니다.
두 안 모두 현재는 미정이며, Python을 선택해도 웹의 모든 서버 기능을 반드시 제거해야 하는 것은 아닙니다.

## 현재 생성한 폴더의 의미

`backend/`, `ingestion/`, `eval/`, `infra/`는 역할별 논의를 시작할 공간입니다.
각 폴더의 README만 만들었으며 코드·자료를 옮기거나 의존성을 설치하지 않았습니다.
백엔드 언어를 정한 뒤 필요한 내부 모듈·테스트·패키지 설정을 만들 수 있습니다.
